# DisplayApp

Android cockpit for a **Bluetooth Low Energy (BLE/GATT)** telemetry source. Decodes Cap'n Proto frames in realtime, persists trips in Room, and renders a Jetpack Compose UI with live charts, map navigation, and trip replay. compileSdk `36.1` (Android 16 QPR1), minSdk 24.

> The transport was migrated from Bluetooth Classic (SPP/RFCOMM) to BLE — see [`docs/BLE_MIGRATION.md`](docs/BLE_MIGRATION.md). The controller's BLE contract is [`docs/EVDISPLAY_BLE_COMMUNICATION.md`](docs/EVDISPLAY_BLE_COMMUNICATION.md) (device `EVdisplay`, service `0xAF00`, notify `0xAF08`).

## Build & run

```bash
./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n com.innodrive.evdash/.MainActivity
```

**Toolchain:** AGP `9.1.1` · Kotlin `2.2.10` · Gradle `9.3.1` · Compose BoM `2024.09.00` · JDK 11 source/target · KSP for Room.

**Release / Play Store.** `applicationId` + `namespace` are `com.innodrive.evdash` (renamed off `com.example.*`, which Play rejects). Play wants an App Bundle, not an APK — build `./gradlew bundleRelease` (→ `app/build/outputs/bundle/release/app-release.aab`). Release signing reads `RELEASE_STORE_FILE`/`_PASSWORD`/`RELEASE_KEY_ALIAS`/`_PASSWORD` from `local.properties` (or CI env); when unset the release build falls back to the debug key (local smoke-test only). Full keystore + Play Console checklist: [`docs/RELEASE.md`](docs/RELEASE.md).

**Map + routing keys (optional):** the map is **MapLibre GL** (open-source, no Google Maps) and routing/geocoding is **GraphHopper** (hosted Directions + Geocoding API). Add to `local.properties`:

```
MAP_STYLE_URL=https://api.maptiler.com/maps/streets-v4/style.json?key=…   # any MapLibre style (MapTiler/Stadia/Protomaps/self-hosted)
GRAPHHOPPER_API_KEY=…
```

The build inlines both via `BuildConfig.MAP_STYLE_URL` / `BuildConfig.GRAPHHOPPER_API_KEY`. Both are **secrets** — `local.properties` is gitignored; never commit them. Without a style URL the app still builds — `MapStyleGate` shows a placeholder instead of the map; without a GraphHopper key search/routing return empty (the ports report `isConfigured = false`).

## Architecture

Clean layering under `app/src/main/java/com/innodrive/evdash/`:

| Layer | Subpackages | Notes |
|---|---|---|
| `data/` | `bluetooth/{ble,connection,controller}` · `protocol/` · `persistence/{entity,dao,export}` · `energy/` · `preferences/` · `simulator/` · `system/` · `location/` · `replay/` · `sharing/` · `diagnostics/` · `format/` · `permissions/` · `repository/` · `navigation/{graphhopper}` | BLE GATT client (`BleGattClient`) + Cap'n Proto framing + `Crc16`; adapter/discovery surface (`BleController`) feeds the quick-settings sheet independently of the BLE pipeline; Room schema with explicit `Migration` list (no destructive fallback); pure-Kotlin energy integrators (`EnergyAccumulator`, `EfficiencyTracker`); DataStore-backed user prefs (`AppPreferences`); hardware-free simulator with scenarios, fused-location repo, Room-backed trip replay, FileProvider-based CSV sharing, formatters, diagnostics + permission probes; **`navigation/`** is the provider-agnostic routing/navigation layer (`RouteNavigator`, `NavigationCoordinator`, `RouteProgressTracker`, `GeoMath`, GraphHopper impls of the `RoutePlanner`/`NavigationProvider`/`Geocoder` ports). `app/schema/{telemetry,navigation}.capnp` are the Cap'n Proto schemas (Room schemas are not exported — `exportSchema = false`) |
| `domain/` | `model/` · `repository/` · `replay/` | Pure Kotlin: `VehicleData`, `GeoLocation`, `Route`, `ChargingStation`, `AppSettings` + unit enums; navigation domain (`RoutePlan`/`RouteManeuver`, `NavProgress`/`NavState`/`Maneuver`, `GeoPlace`) + ports (`NavigationProvider`, `RoutePlanner`, `Geocoder`); repository interfaces, `TripReplaySource` |
| `presentation/` | `viewmodel/` · `state/` · `navigation/` · `ui/{dashboard,charts,connection,device,maps,logs,settings,permissions,components,common,icons}` | One ViewModel per cockpit tab + a `RootViewModel` for activity-wide state, `@Immutable` UI states, `EvIcons` (no `material-icons-extended` — saves ~22 MB), reusable `GlassCard`/`SectionHeader`/`StatusChip`. `ui/connection/` hosts the shared Bluetooth surfaces (`BluetoothQuickSheet`, `BluetoothStatusPopover`, `BluetoothDeviceRow`) — both the Drive header and `DeviceScanScreen` drive them through a single `BluetoothViewModel`. `ui/maps/` holds the renderer-neutral `MapProvider` abstraction (`MapLibreMapProvider` impl) + `CockpitMap`/`MiniMapCard`/`NavigationScreen`, all driven by one `MapsViewModel` |
| `service/` | `TelemetryService` | Foreground service (`foregroundServiceType="connectedDevice"`) that owns the live BLE session so it survives backgrounding |
| `di/` | `AppContainer` | Manual DI; constructed once in `DisplayApp.onCreate` |
| `ui/theme/` | `Color`, `Dim`, `Shapes`, `Type`, `Theme`, `TelemetryPalette` | EV-blue Material palette; `TelemetryPalette` is the per-metric color identity (light + dark tunings) provided via `LocalTelemetryPalette`; `Dim` is the only source of dp tokens |

**Single-activity host.** `MainActivity` → `RootViewModel` (theme + `AppSettings`) → `DisplayAppTheme` → `ProvideAppSettings` → `PermissionHandler` → `AppNavHost`. One `Scaffold` + one `NavHost`. Bottom bar (`Drive`/`Chart`/`Logs`) shows only on cockpit routes; `Scan`/`Navigation`/`Settings`/`Developer`/`TripDetail` are full-bleed.

## Notable patterns

- **`LocalAppSettings` CompositionLocal** ([`AppSettingsAmbient`](app/src/main/java/com/innodrive/evdash/presentation/ui/common/AppSettingsAmbient.kt)) exposes the live `AppSettings` snapshot to any composable. Units (km/h ↔ mph, °C ↔ °F, 12h ↔ 24h) are a *display* concern — converting at the consumer keeps domain types SI and avoids threading prefs through every per-screen ViewModel. Reads are scoped: composables that don't read `LocalAppSettings.current` don't recompose on a unit change. Telemetry/domain is **always** km/h + °C; conversion happens only at the display layer (e.g. `SpeedUnit.convertFromKmh`, `TemperatureUnit.convertFromCelsius`).
- **`RootViewModel`** is the activity-scoped state hub — it merges theme settings + `AppSettings`. Provider tree in `MainActivity` lives outside `AppNavHost` so per-route ViewModels never see preferences.
- **Charts ViewModel** ([`ChartsViewModel`](app/src/main/java/com/innodrive/evdash/presentation/viewmodel/ChartsViewModel.kt)) uses fixed-capacity `ArrayDeque` ring buffers + 10 fps emit throttle (`EMIT_INTERVAL_MS = 100`). Tweak source-rate via `SOURCE_HZ` if the protocol changes.
- **Multi-line chart Y-axis** uses per-metric normalization with a *focused metric* driving the visible Y tick labels — see [`RealtimeLineChart.niceRange`](app/src/main/java/com/innodrive/evdash/presentation/ui/charts/RealtimeLineChart.kt). Battery has a fixed `0..100` range; others auto-scale with 12% padding. The focused line is rendered thicker (`FOCUSED_STROKE_DP`) over a soft gradient fill; non-focused selected lines drop to `UNFOCUSED_ALPHA` so the focal series reads first during glance analysis. Y-axis labels are tinted the focused metric's color so the axis ticks self-describe which series they're scaled to.
- **TelemetryPalette is the only source of metric color.** [`TelemetryPalette`](app/src/main/java/com/innodrive/evdash/ui/theme/TelemetryPalette.kt) maps each [`TelemetryMetric`](app/src/main/java/com/innodrive/evdash/presentation/state/TelemetryMetric.kt) to a (light, dark) color pair; `DisplayAppTheme` provides the active impl via `LocalTelemetryPalette`. Call sites resolve a color with `metric.seriesColor()` — chip dot, line stroke, marker halo, axis tick label, Drive tile accent, Trip Detail stat label all share one identity per metric. Future overlay treatments (fault outline, thermal warning, regen segment, SoH badge) hang off `OverlayKind` so the visual language scales without scattering raw `Color()` literals across screens.
- **Fullscreen chart** ([`ChartsFullscreenScreen`](app/src/main/java/com/innodrive/evdash/presentation/ui/charts/ChartsFullscreenScreen.kt)) is a `Dialog` overlay (not a nav route) so it shares the same `ChartsViewModel` instance — state is preserved on entry/exit by definition. Orientation lock + immersive bars in a `DisposableEffect`; `rememberSaveable` keeps the flag alive across config changes. The layout drops the card-shell padding and switches `MetricToggleChips` into `compact = true` so the chart claims maximum landscape real estate.
- **Telemetry replay** (`TripDetail`) swaps the source: `RoomTripReplaySource` produces a `Flow<VehicleData>` from persisted samples, the same chart/dashboard composables consume it. Live vs replay is one repository, two impls.
- **Device Information Service.** On connect, [`BleGattClient`](app/src/main/java/com/innodrive/evdash/data/bluetooth/ble/BleGattClient.kt) reads DIS (`0x180A`) Model (`0x2A24`) + Firmware (`0x2A26`) as the **final handshake step** (after the CCCD subscribes, before `ready` completes — so no app write can collide with the reads); absent service/chars or a failed read are skipped, never blocking a connect. Result flows as `DeviceInfo` through the data source → `VehicleRepository` → `DashboardUiState` to the Home "Vehicle Information" card (Firmware/Model), which shows "—" when disconnected or the board has no DIS. `SwitchableDataSource` mirrors `deviceInfo` like its other delegate flows — a facade that forgets to forward a new flow is a silent bug (the interface default returns null).
- **Firmware/Model prefer the telemetry stream over DIS.** The board now streams its running firmware as `fwVersion` @17 (packed semver) and its controller identity as `controllerType` @23 on every telemetry frame. `DashboardViewModel` resolves the Home card's **Firmware** as `firmwareVersionName(data.firmwareVersion)` first (authoritative running version), falling back to the static DIS revision string; **Model** keeps the DIS model number (the specific vehicle model, e.g. "GESITS G-1") as primary and falls back to `controllerTypeName(data.controllerType)` (0 → "VOTOL EM-100", 1 → "NANJING") only when connected and DIS has none. Both helpers live in [`VehicleData.kt`](app/src/main/java/com/innodrive/evdash/domain/model/VehicleData.kt).
- **Bluetooth split into two surfaces.** `BluetoothDataSource` + `TelemetryService` own the BLE/GATT connection — the data plane. [`BleController`](app/src/main/java/com/innodrive/evdash/data/bluetooth/controller/BleController.kt) (impl of the transport-neutral [`BluetoothController`](app/src/main/java/com/innodrive/evdash/data/bluetooth/controller/BluetoothController.kt) interface) owns the *adapter/discovery* plane: power state, **BLE scan filtered on service `0xAF00`** with RSSI, `forget`. The controller is independent so opening the quick sheet never touches the live BLE session. Connect/disconnect from the sheet still routes through `TelemetryService` so the foreground notification + lifecycle stay identical whether the user came from the header or `DeviceScanScreen`.
- **Single Bluetooth ViewModel.** [`BluetoothViewModel`](app/src/main/java/com/innodrive/evdash/presentation/viewmodel/BluetoothViewModel.kt) merges the controller, `VehicleRepository.connectionState`, and `DevicePreferences` into one `BluetoothUiState`. Both the Drive header's [`BluetoothQuickSheet`](app/src/main/java/com/innodrive/evdash/presentation/ui/connection/BluetoothQuickSheet.kt) and `DeviceScanScreen` instantiate this VM with the same factory args, so the two surfaces stay in sync (scan results, paired list, pending-connect spinner) without an extra repository layer.
- **Header BT icon has two gestures.** Tap → [`BluetoothStatusPopover`](app/src/main/java/com/innodrive/evdash/presentation/ui/connection/BluetoothStatusPopover.kt) (compact status + reconnect/disconnect). Long-press → `BluetoothQuickSheet` (full management). The popover anchors to the icon via the `bluetoothAnchor` slot in `BrandHeader`; the sheet is a sibling of the cockpit content at the `NavHost` level with `rememberSaveable` flags. Long-press always fires `HapticFeedbackType.LongPress`.
- **Energy split: lifetime vs. rolling.** [`EnergyAccumulator`](app/src/main/java/com/innodrive/evdash/data/energy/EnergyAccumulator.kt) is a pure trapezoidal V × I × dt integrator owned by `TripSessionManager` — one instance per trip, persisted as `TripEntity.energyUsedWh`/`energyRegenWh`. [`EfficiencyTracker`](app/src/main/java/com/innodrive/evdash/data/energy/EfficiencyTracker.kt) is a *rolling* 60 s window with EWMA smoothing that drives the Drive page's Wh/km tile and range estimate; it resets on `DISCONNECTED`. Both are deterministic (no clock reads — timestamps come from `VehicleData`) and unit-tested (`EnergyAccumulatorTest`, `EfficiencyTrackerTest`).
- **Trips auto-record; the card reads the newest completed one.** [`VehicleRepositoryImpl`](app/src/main/java/com/innodrive/evdash/data/repository/VehicleRepositoryImpl.kt) drives the recording lifecycle off the live telemetry stream it already owns — `TripSessionManager.startTrip()` on first movement while `CONNECTED`, `stopTrip()` on `DISCONNECTED` (`RECONNECTING` left alone so a watchdog re-scan doesn't split a ride). `stopTrip` discards sub-50 m rolls; `discardDanglingTrips()` runs at startup (before any session opens) to drop trips a killed process left in-progress. The Home "Last Ride" card / Logs then read the newest completed trip. **Nothing else calls `startTrip`.**
- **Fault detection is condition-based, not just the wire bitfield.** [`FaultDetector`](app/src/main/java/com/innodrive/evdash/data/fault/FaultDetector.kt) is a pure, edge-triggered detector (over-temp with hysteresis, low-battery via `flags` bit6, controller `faultCode`) run from `TripSessionManager.onTelemetryUpdate` on every frame; rising edges persist `FaultEventEntity` rows (linked to the active trip, or null when idle). The Trip Detail **Faults** section renders them. `faultCode` is PROVISIONAL on the wire (firmware sends 0), so today the real triggers are temp + low-battery.
- **Drive stays awake + warns on critical battery.** [`DashboardScreen`](app/src/main/java/com/innodrive/evdash/presentation/ui/dashboard/DashboardScreen.kt) drives `View.keepScreenOn` from the connection state (held while `CONNECTED`, released on disconnect or when Drive leaves composition) so the handlebar cockpit never sleeps mid-ride. A `LowBatteryBanner` renders at the top of Drive when the pack is known, not charging, and in the `CRITICAL` band (≤ 20 %), with the rolling range as context; dismiss is sticky per 5 % bucket so a worsening pack nags again. Pure UI — all fields already on `DashboardUiState`.
- **Navigation is provider-agnostic end to end.** The map renderer, the routing/geocoding SDK, and the BLE navigation protocol are three independent ports — swap any one without touching the others. `NavProgress` (per-fix nav state) + `RoutePlan` (neutral geometry) are the single source of truth that drives **both** the phone map overlay **and** the controller. Ports: [`RoutePlanner`](app/src/main/java/com/innodrive/evdash/domain/repository/RoutePlanner.kt) (text/coords → `RoutePlan`), [`Geocoder`](app/src/main/java/com/innodrive/evdash/domain/repository/Geocoder.kt) (search + `reverse`), [`NavigationProvider`](app/src/main/java/com/innodrive/evdash/domain/repository/NavigationProvider.kt) (emits `progress` + `activeRoute`). Today all three are GraphHopper (`data/navigation/graphhopper/`, hosted Directions/Geocoding via `HttpURLConnection` + `org.json`, zero new deps); the free-tier default profile is `car` (`scooter` needs a plan that enables it → HTTP 400 otherwise). A shared [`GraphHopperHttp`](app/src/main/java/com/innodrive/evdash/data/navigation/graphhopper/GraphHopperHttp.kt) helper drains + parses the error body, classifies the status into a typed `GraphHopperError` (network / 429 / 401 / 400 / 5xx), and **retries transient failures** with bounded backoff (fails fast on auth/bad-request); `RoutePlanner`/`Geocoder` expose a provider-neutral `lastError` so the `DestinationConfirmSheet` shows the real reason (bad key / quota / offline) via `NavigationCoordinator.previewError` → `MapsUiState.previewErrorMessage`, not a generic "can't route". `RouteProgressTracker` (map-matching/off-route/arrival) + `GeoMath` are provider-independent.
- **One navigation session, explicit lifecycle.** [`NavigationCoordinator`](app/src/main/java/com/innodrive/evdash/data/navigation/NavigationCoordinator.kt) (app-scoped singleton) runs **preview → confirm → navigate**: `preview(dest)` plans the route and exposes `previewDestination`/`previewRoute` for the `DestinationConfirmSheet` (name/address, distance, ETA) + a map preview — **no session started**; `startPending()` on confirm creates the session via [`RouteNavigator`](app/src/main/java/com/innodrive/evdash/data/navigation/RouteNavigator.kt); `dismissPreview()`/`cancel()` back out. Both a search pick and a long-press-drop-pin funnel through `MapsViewModel` into the same coordinator. `RouteNavigator` streams the session's `NavProgress` to BLE and re-seeds on reconnect.
- **BLE navigation protocol is a separate, frozen schema on its own characteristic.** [`navigation.capnp`](app/schema/navigation.capnp) (NOT `telemetry.capnp`) + hand-built encoders in [`NavigationSchema`](app/src/main/java/com/innodrive/evdash/data/protocol/NavigationSchema.kt) frame three message types over **`0xAF06` WRITE** (not multiplexed on `0xAF07`): `RouteSummary` (navType `0x01`, once), `RouteChunk` (`0x03`, the downsampled route polyline as `List(Int16)` deltas — sent on a new route), and `NavInstruction` (`0x02`, streamed turn-by-turn). All byte-verified against the `capnp` CLI in `NavigationFrameTest`. Firmware contract: [`docs/NAVIGATION-INTEGRATION.md`](docs/NAVIGATION-INTEGRATION.md).
- **Renderer-neutral map** ([`MapProvider`](app/src/main/java/com/innodrive/evdash/presentation/ui/maps/MapProvider.kt)): the UI depends only on `MapProvider` + plain types (`MapCameraState`, `MapContent`, `FitPadding`), never on MapLibre. `MapLibreMapProvider` draws the route line / location puck / destination pin as runtime GeoJSON layers. **Camera modes:** follow (heading-up once navigating, battery-conscious move gate) vs. **fit** — `fitBounds` frames the whole route, applied once per `fitToken` bump (new destination or the **Overview** button), so a user pan is never overridden; reroutes stay in follow. Fit padding is **measured responsively** (search-bar bottom + bottom-card top via `onGloballyPositioned`), not fixed px. `MapStyleGate` reads `BuildConfig.MAP_STYLE_URL` and renders a placeholder when empty.
- **Developer Mode** is hidden behind tapping the Settings → About → Version row 7 times. Unlock persists in `AppSettings.devModeUnlocked`. Reveals the `Developer` route which surfaces the diagnostics overlay toggle, simulator scenarios, and other runtime probes.

## Gotchas

- **Compose BoM 2024.09.00 + `FlowRow`**: foundation-layout 1.7 lacks the `maxLines`/`overflow` overload that Kotlin resolves against if you import `FlowRow`. Runtime `NoSuchMethodError`. Prefer `Row(Modifier.horizontalScroll(...))` until BoM is bumped past 1.8.
- **`MainActivity` has `configChanges="orientation|screenSize|screenLayout|keyboardHidden"`** — the fullscreen chart relies on this so rotation doesn't destroy the Activity (and the Dialog with it). Removing it will break that flow.
- **Emulator stuck at boot** (API 36.1 in particular): if `adb shell pm list packages` returns `Can't find service: package`, the AVD's PackageManager never started. Recover with:
  ```bash
  adb -s <serial> emu kill
  ~/Android/Sdk/emulator/emulator -avd <AvdName> -no-snapshot-load -wipe-data
  ```
- **Custom Compose icons**: when adding a new icon, extend [`EvIcons`](app/src/main/java/com/innodrive/evdash/presentation/ui/icons/EvIcons.kt) with raw `ImageVector` path data. Do **not** add the `material-icons-extended` dependency.
- **No default arg on a `@Composable` *interface* method.** `MapProvider.Map(...)` deliberately declares `onLongPress` with **no** default — a default value on a composable interface function makes the Compose compiler generate a `$default` bridge that desyncs from the overrides, throwing `AbstractMethodError` at runtime (often only after an incremental build). Callers pass it explicitly (see `CockpitMap`). If you hit a mysterious `AbstractMethodError` on a composable, do a clean build and check for interface defaults.
- **MapLibre lifecycle + gestures.** `MapLibreMapProvider` forwards the composition lifecycle to the `MapView` in a `DisposableEffect` (MapLibre requires `onStart/Resume/Pause/Stop/Destroy`). The long-press listener uses `rememberUpdatedState` so it isn't reinstalled on recomposition. Camera moves use `easeCamera` (animated); the follow gate skips sub-8 m / sub-4° jitter to stay battery-friendly on the always-on Drive mini-map.
- **`TelemetryService` is `START_STICKY` — handle the null-intent restart.** When the OS kills and re-creates the foreground service it re-invokes `onStartCommand` with a **null intent**. The `when (intent?.action)` **must** have an `else` that calls `startForeground(...)` promptly (Android 12+ throws `ForegroundServiceDidNotStartInTimeException` otherwise) and re-runs `autoConnect()`, or the telemetry link silently never resumes after a background kill. Don't drop that branch.
- **Trip CSV sharing**: `ShareHelper` uses an authority of `${applicationId}.fileprovider`. Paths exposed are in [`res/xml/file_paths.xml`](app/src/main/res/xml/file_paths.xml) — add new dirs there if a future exporter writes outside cache.
- **Room migrations are real, not destructive.** [`TelemetryDatabase`](app/src/main/java/com/innodrive/evdash/data/persistence/TelemetryDatabase.kt) declares an explicit `MIGRATIONS` array (`MIGRATION_1_2` … `MIGRATION_6_7`, DB **version 7**; the latest adds per-sample `faultCode`/`flags` to `telemetry` for replay). Every migration is covered by [`TelemetryDatabaseMigrationTest`](app/src/androidTest/java/com/innodrive/evdash/data/persistence/TelemetryDatabaseMigrationTest.kt) (hand-built source schema → `migrate()` → assert new columns + preserved rows). `fallbackToDestructiveMigration()` is **not** wired up — drop a trip table by accident and you lose user history. Bumping the entity = bumping `version` + appending a `Migration(from, to)`. `exportSchema = false`, so there's no generated JSON to commit; verify migrations by running the app against the prior debug install.
- **`BLUETOOTH_SCAN` declared with `neverForLocation`.** We BLE-scan **filtered on the controller's service UUID (`0xAF00`)** only to find/reconnect the vehicle, and never derive location from scan results — so the flag lets Android 12+ scan without Location Services on. (Bonus: a filtered scan keeps delivering results with the screen off, which is what makes background reconnect work — an *unfiltered* scan is throttled/blocked screen-off, so keep the `0xAF00` filter.) `ACCESS_FINE_LOCATION` is declared for all versions (the map/navigation needs precise fixes); on Android 11 and below it also gates BLE scanning.
- **A stalled BLE link doesn't always raise a GATT disconnect, so a silent stall can leave the session "connected" with no data.** An out-of-range or wedged controller may stop notifying without a clean `onConnectionStateChange`. [`BleDataSource`](app/src/main/java/com/innodrive/evdash/data/bluetooth/ble/BleDataSource.kt) arms a **frame watchdog** (`runFrameWatchdog`): `onCharacteristicChanged` stamps `lastDataElapsedMs` (`@Volatile`, monotonic `elapsedRealtime`) on every notification, and the watchdog polls every `WATCHDOG_POLL_INTERVAL_MS` (1 s) and force-closes the GATT once silence exceeds `FRAME_WATCHDOG_TIMEOUT_MS` (3 s ≈ 30 missed frames at ~10 Hz) — or `INITIAL_DATA_TIMEOUT_MS` (8 s) before the first notification arrives, since CCCD-subscribe + connection-interval negotiation can legitimately delay it. The close routes into the normal `handleConnectionLost()` → **reconnect-by-rescan** path (rescans service `0xAF00`, reusing `ReconnectPolicy` backoff). Separately, an adapter-state receiver drops straight to `DISCONNECTED` when the phone's Bluetooth is turned off. Tune `FRAME_WATCHDOG_TIMEOUT_MS` if the notify rate changes — too tight and normal jitter false-trips it.

## Canonical telemetry invariants (Phase 1 audit)

**One pipeline, one derivation site, one display rule.** These are the rules that
keep Drive / Charts / Logs / Trip Detail / replay / CSV exporting the same
number for the same wire frame.

- **Wire schema is the frozen `VotolTelemetry`.** The board's app-facing spec is [`docs/capnpble_new.md`](docs/capnpble_new.md) (the current `@0..@23` schema; supersedes `capnpble.md`, `EVDISPLAY_BLE_COMMUNICATION.md`, and the payload-only `capnp.md`); [`telemetry.capnp`](app/schema/telemetry.capnp) mirrors it. **Post-2026-07-07 renumber, ordinals @0..@14 are FROZEN** (sequential declaration order; a one-time wire-breaking re-sort that moved every byte offset, grew the data section 24→32 B and added `batteryCurrent` @2, `tempBattery` @8, `odoMeters` @12, `tripMeters` @13). **Append-only since**, all frozen: `tripAMeters` @15 / `tripBMeters` @16 (trip A/B, 2026-07-07; `tripMeters` @13 is now a legacy alias mirroring @15), `fwVersion` @17 / `otaState` @18 / `otaProgress` @19 (OTA, 2026-07-13, board→app TX-only), `phaseA` @20 / `phaseC` @21 / `power` @22 (NANJING per-phase/power, 0 on VOTOL) / `controllerType` @23 (0 VOTOL EM-100, 1 NANJING; labels the Model as a fallback when DIS has none — see the Firmware/Model pattern above). The data section is now **56 B / 7 words**, framed payload **72 B (LEN `0x48`)**, frame 76 B. Each `0xAF08` notification carries one framed `[0xAA][LEN:uint8][capnp payload][CRC16-CCITT-LE]` message (CRC over `LEN‖payload`), ~10 Hz; at MTU ≥ 79 that's one frame per notification, otherwise the byte-stream `FrameDecoder` reassembles across notifications. [`TelemetrySchema.readFrom`](app/src/main/java/com/innodrive/evdash/data/protocol/TelemetrySchema.kt) is **length-aware** — a legacy short frame (pre-@15) decodes with the missing trailing fields = 0 (it rejects only a payload too short to hold the 16-byte capnp envelope). New fields append at @24+ and grow `LEN` — always honor `LEN`, never assume a fixed length.
- **Single decode path.** Live frames flow through `TelemetryMapper` (wire → `VehicleData`); persisted samples flow through [`TelemetryDerivations.decodeEntity`](app/src/main/java/com/innodrive/evdash/data/protocol/TelemetryDerivations.kt) (Room row → `VehicleData`). Every consumer downstream — replay, CSV, Trip Detail charts — reads the resulting `VehicleData`. `rpm` and `speedKmh` are now **real wire fields** (read straight off the frame, not derived); `power` is still derived in `TelemetryDerivations`. No screen, ViewModel, or exporter may re-derive `power` locally; adding a new derivation = adding a function to `TelemetryDerivations` and calling it from both sites. **Wire scaling ≠ persistence scaling** — the wire carries deci-volts/direct-km/h, while `TelemetryLogger` stores its own fixed-point (×10/×100) that `decodeEntity` inverts via the `*FromEntity` helpers; the two are decoupled so a wire revision never forces a Room migration.
- **Current is calibrated (signed deci-amps).** `currentMotor` (@3) is **CONFIRMED** as deci-amps (÷10 = A) with negative = regen — see [`docs/PENDING_FIRMWARE_CURRENT_CALIBRATION.md`](docs/PENDING_FIRMWARE_CURRENT_CALIBRATION.md) (now resolved). So `power = voltage × current`, `EnergyAccumulator`, `EfficiencyTracker` (Wh/km, range) and regen accounting are **live** on real hardware. `TelemetryConstants.CURRENT_CHANNEL_CALIBRATED = true` gates the "—" fallback (flip to false to restore it). `TelemetryMapper` applies `frame.currentMotor / 10f` (idle ~0.4 A zero-offset left unsubtracted); the simulator emits `amps × 10` so the ÷10 decode round-trips. Current & Power show on the Drive grid, are selectable Chart series, and render on Trip Detail.
- **rpm is a wire field.** `VotolTelemetry.rpm` (@4) arrives directly; `kmh` (@5) is the board's `rpm*83/1000`. The legacy `rpmFromSpeedKmh` (speed×100) survives ONLY as the `decodeEntity` fallback for pre-v6 rows recorded before rpm was persisted.
- **Battery pack temperature is a real wire channel** (`tempBattery` @8, since the 2026-07-07 renumber). `TelemetryMapper` maps it to `VehicleData.batteryTemperature` with `batteryTempAvailable = true`; the Battery-Temp tile/series are live. (Persisted rows recorded before this still decode 0.)
- **Odometer + pack current are on the wire.** `odoMeters` @12 (lifetime) / `tripMeters` @13 (legacy alias of trip A) are board-integrated metres → `VehicleData.odometerKm`/`tripKm` (÷1000); the Home "Odometer" tile prefers the wire lifetime value, falling back to integrated session distance when it's 0. The two independent trip meters `tripAMeters` @15 / `tripBMeters` @16 surface as `VehicleData.tripAKm`/`tripBKm`. `batteryCurrent` @2 is signed pack amps (positive = charging) → `VehicleData.batteryCurrent`. Trip reset is a `PhoneNotification` control command (`category=32`, `title="ODO_RESET_TRIP"` legacy / `"ODO_RESET_TRIP_A"` / `"ODO_RESET_TRIP_B"`) written to `0xAF07` — wired to the Home **Trip A → Reset** action via `DashboardViewModel.resetTripOdometer()`.
- **OTA status fields are decoded but the install flow is not built yet.** `fwVersion` @17 / `otaState` @18 / `otaProgress` @19 are decoded onto `VehicleData` (`firmwareVersion`/`otaState`/`otaProgress`), so an `OtaController` can be driven off the telemetry flow. The **firmware-frozen v1 contract** — phone hosts the new `lvgl_evdash` binary over HTTP on the hotspot, sends an `OTA_INSTALL{url,ver,sha256}` control command (`category=32`, `title="OTA_INSTALL"`) over `0xAF07`, and renders progress from `otaState`/`otaProgress` — is specified in [`docs/OTA-FIRMWARE-INTEGRATION-RESPONSE.md`](docs/OTA-FIRMWARE-INTEGRATION-RESPONSE.md) but **not yet implemented** (no `OtaController`, HTTP host, or OTA UI). NANJING-only `phaseA`/`phaseC`/`power` @20..@22 are decoded into the wire struct but intentionally **not** surfaced — `VehicleData.power` stays the derived V×I so the single-derivation invariant holds (the wire `power` is 0 on VOTOL).
- **No wire timestamp.** `VehicleData.timestamp` is wall-clock-at-decode. The v1 wire has no timestamp field; `seq` (@9, rolling UInt32) covers frame ordering + drop detection instead.
- **One `dt` clamp.** All integrators (`EnergyAccumulator`, `EfficiencyTracker`, `TripSessionManager` distance, Drive session distance) clamp inter-sample `dt` to [`TelemetryConstants.MAX_SAMPLE_DT_MS`](app/src/main/java/com/innodrive/evdash/data/protocol/TelemetryConstants.kt). Don't introduce a screen-local clamp; trip distance vs Drive session distance must drift only through different aggregation windows, never through different gap policies.
- **Diagnostics is end-to-end live.** Frame decoding, CRC errors, and sync losses report directly from `FrameDecoder` into `DiagnosticsRepository`; the Dashboard ViewModel passes that snapshot through to `DiagnosticsState` — no zero placeholders, no UI-local accounting. FPS is computed in the VM and pushed via `reportFps()` so Settings and the overlay read the same number.
- **Display-layer unit conversion only.** Chart series stay in SI (km/h, °C); km/h↔mph and °C↔°F are applied at the label site (see `StaticTelemetryChart.displayConverter`). A unit preference change must update labels without rebuilding datasets.

The target invariant: **Drive page == Charts == Logs == Trip Detail == Replay == CSV** for any given wire frame. Phase 2 persisted `rpm`/`power` columns so a future change to the derivation formula doesn't retroactively alter recorded trips; Phase 4 persists `faultCode`/`flags` on telemetry rows (schema v7) so replay/CSV/Trip Detail match live, and a condition-based [`FaultDetector`](app/src/main/java/com/innodrive/evdash/data/fault/FaultDetector.kt) logs discrete `FaultEventEntity` rows (over-temp / low-battery / controller-fault) that the Trip Detail **Faults** section surfaces.

## Conventions

- Compose-only UI; no XML layouts.
- Coroutines + `Flow`; ViewModels expose `StateFlow`. UI states are `@Immutable` data classes.
- **Units are SI in the domain, converted at display.** Read `LocalAppSettings.current` and use the unit enum's `convertFromX`/`formatX` helpers rather than mutating telemetry values.
- Logging via Timber (`Timber.tag(...).d(...)`).
- Hardware-free dev: use the `data/simulator/` source instead of real BT.
- When bumping a Room entity, write a new `Migration` and append it to `TelemetryDatabase.MIGRATIONS` — destructive fallback is disabled on purpose. Old rows should default to a value the UI can render as "—" (see how `energyUsedWh = 0.0` is handled) so legacy data isn't misleadingly precise.
- Spacing only via `Dim` tokens — no inline `.dp` literals in screen-level composables.
- **Telemetry series colors only via `TelemetryMetric.seriesColor()`** (or `LocalTelemetryPalette.current` if you need to render outside a composable scope). Don't reach for `EvBlue`/`EvLime`/etc. for anything that represents a plottable channel — the palette already encodes the right per-mode tuning. Status indicators (`Recording`, error tints) can still use the semantic accents directly.

## Local config

`local.properties` is per-machine (`sdk.dir`, `MAP_STYLE_URL`, `GRAPHHOPPER_API_KEY`, and the release-signing `RELEASE_STORE_FILE`/`RELEASE_STORE_PASSWORD`/`RELEASE_KEY_ALIAS`/`RELEASE_KEY_PASSWORD`) and gitignored — do not commit. The style URL, GraphHopper key, and all signing material are secrets; `*.jks`/`*.keystore` are gitignored too.
